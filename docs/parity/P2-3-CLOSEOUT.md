- Added `BankRepository.transact(...)` with an explicit `BankMutation` proposal and `BankTransactionResult` outcome. Rejected mutations are not written; mutation exceptions and durable-write failures restore the snapshot before returning failure.
- Routed bank deposit, auto-deposit, withdrawal, and free/paid tab-unlock vault changes through the transaction boundary.
- Bank success events are now published only after the repository reports a durable commit. A failed paid unlock immediately refunds the removed emeralds when the vault commit fails; crash/restart recovery for that cross-system payment remains open for the journal slice.

- Added quest reward preflight and a typed `QuestCompletionResult`: unknown faction rewards and non-atomic command rewards are rejected before state or reward mutation; supported completion marks `COMPLETED` only after reward fan-out and progression persistence return successfully. P1-1 now persists a completion-pending request intent with objective progress and retries only while the exact quest-local state revision remains eligible.
- Added owned `TradeListing.TradeReservation` tokens. Live trade execution now reserves a specific use, compensates payment on output failure, and rolls back only its own reservation; concurrent successful uses are not decremented by another trade's failure.
- Wired trade request IDs through `StoryNpcsNetwork` into the canonical service and added a durable `trade.execute` journal with bounded listing/payment intent, subject binding to player/NPC/listing, duplicate replay, and terminal rejection classification.
- Added `TradeStateRepository` for durable per-NPC/listing use counts, wired indexed live trades through durable reserve/rollback, hydrated the trade screen from that state, and excluded runtime `uses` from YAML definition writes.
- Added fail-closed validation for semantically corrupt listing-use records, including negative counts, so invalid durable state cannot become a client projection.
- Added `DurableOperationJournal` with bounded operation identity fields, preserved prepared intent, subject-filtered pending queries, durable `PREPARED`/`COMMITTED`/`ABORTED` lifecycle states, replay classification, terminal-transition protection, corruption/future-record refusal, and durable-store failure fixtures.
- Wired the live held-item bank deposit through `StoryNpcsApplicationService.depositHeldToBank(...)`: it plans a fixed slot, records the item/tag/count intent, persists a vault-side operation marker with the bank commit, owns main-hand removal after that commit, and returns `APPLIED`, `REPLAYED`, `REJECTED`, or `RECOVERY_REQUIRED`. The network adapter no longer clears the held stack independently.
- Added login-time bank-operation replay. Pending held deposits with no durable vault marker are safely aborted under the deferred-inventory protocol; marked bank commits are reconciled and marker cleanup is retried. A second marker phase prevents cleanup retries from shrinking the inventory twice.
- Fixed replay ordering in the bank packet adapter: committed deposit retries reach the service before any empty-hand check, so a successful prior commit can return `REPLAYED` after reconnect or inventory resynchronization.
- Added deterministic persisted `listingId` identities for trade contracts and moved durable listing-use state and trade journal subjects from client/index identity to that stable identity.
- Added transport duplicate admission classification and stable request-ID reuse in trade and bank screens; duplicate trade and held-item-deposit requests now reach the canonical durable replay path where one exists.
- Added a subject-bound `bank.withdraw` durable request journal: committed retries are classified as `REPLAYED`, prepared retries fail closed as `RECOVERY_REQUIRED`, request-ID conflicts are rejected, and network withdrawals now pass the client request ID into the service.
- Added login-time withdrawal reconciliation. A prepared withdrawal is auto-aborted only when a validated full-stack intent still matches both the exact original vault stack and its captured durable vault revision; removed, changed, merged, identical-restocked, malformed, or otherwise ambiguous state remains `PREPARED` and is reported for manual recovery rather than guessed into a duplicate delivery. The withdrawal transaction also checks the captured revision and item snapshot while holding the repository transaction lock, so a concurrent bank change aborts the request before removal.
- Closed the in-process recovery/withdrawal race with bounded striped locks owned by `DurableOperationJournal`: journaled withdrawal holds its request lock across replay check, prepare, bank mutation, delivery, and terminal journal transition; recovery holds the same lock and rereads current state before aborting. A deterministic two-thread fixture proves recovery waits until an in-flight withdrawal commits.
- A read-only follow-up audit approved this concurrency fix, assuming the production server keeps one live `BankRepository`/journal instance for its bank directory. Multiple concurrently active instances/processes sharing the same directory remain outside the lock guarantee.

## Explicit limits and remaining work

- `completeQuest` now preflights invalid/non-atomic rewards and progression includes a durable completion-pending request intent. A per-reward durable delivery state machine is still needed for crashes between external reward effects and progression persistence.
- Independent review reproduced the XP/item persistence-failure window: player-side rewards can be delivered before completion persistence fails, and retry can deliver them again. Faction rollback does not compensate XP/items. Require recipient-idempotency or a durable claim/recovery protocol before closing this gap. Quest revision advancement is now implemented and tested under P1-1.
- Comparative design evidence: FTB Quests records a claim through `TeamData.markRewardAsClaimed(...)` before invoking `reward.claim(...)`, and stores claimed reward keys in its team data ([claim flow](https://github.com/FTBTeam/FTB-Quests/blob/main/common/src/main/java/dev/ftb/mods/ftbquests/quest/TeamData.java#L2740), [claim persistence](https://github.com/FTBTeam/FTB-Quests/blob/main/common/src/main/java/dev/ftb/mods/ftbquests/quest/TeamData.java#L2376)). This is a useful duplicate-claim guard, but separate team/player persistence does not prove crash-safe exactly-once item/XP delivery; StoryNPCs still needs an idempotent recipient receipt or durable claim mailbox with explicit recovery semantics.
- `executeTrade` now has an in-process reservation/compensation boundary, durable request replay classification, and durable listing-use reserve/rollback state, but live inventory delivery and restart recovery still need operation-specific side-effect markers.
- The durable operation journal primitive is wired into held-item bank-deposit request IDs/login replay and trade request IDs. Quest completion-pending intents are stored in `PlayerProgression`; external quest reward delivery, other bank request IDs, and remaining operation-specific recovery handlers are open.
- Trade journal replay prevents duplicate execution for the same bound request, and listing-use state is now separate from YAML/runtime content. A crash after the durable listing-use reserve but before payment/output completion can still leave the use consumed; live inventory payment/output are not represented by durable side-effect markers, so a prepared trade currently fails closed pending explicit recovery.
- The bank marker proves the vault-side commit, but the live Minecraft inventory is not an atomic durable store. A crash after inventory shrink and before the `inventoryApplied` marker write remains `RECOVERY_REQUIRED`; the current policy refuses to infer success from a matching item/count because a later legitimate deposit can look identical.
- Whole-stack withdrawal now has a durable prepared/committed request record, service-owned delivery compensation, revision-checked mutation, and conservative login reconciliation. A crash after vault removal and before delivery/journal commit can still remain `PREPARED`; this is intentional fail-closed behavior and requires an explicit operator recovery action that is not yet exposed in the UI. The durable vault revision prevents an identical restock from being mistaken for an untouched source stack. Automated fixtures simulate durable restart state; a live Minecraft process-kill/inventory-delivery fixture remains open.
- Paid tab unlock has immediate in-process compensation, but no crash/restart journal spanning emerald payment and vault durability.
- Companion wages, equipment, and world/container effects have no operation-specific exactly-once fixtures yet; faction changes, transport unlocks, and transport requests gained durable dedup/journal coverage in the pass below.
- Quest reward fan-out still needs a durable outbox/ledger; other bank actions and paid unlock still lack crash-spanning journal state.

## P2-3 follow-up pass — login-time quest-completion recovery

- Added `StoryNpcsApplicationService.recoverQuestCompletions(UUID)`, wired into `WorldLifecycleHandler.handlePlayerLogin` alongside bank/trade recovery.
- A durable `PendingQuestCompletion` means a completion was in flight when the process stopped. If the intent is still eligible (same quest-state revision, objectives still met), recovery resumes through `completeQuestUnderLock`: the mark-before-deliver protocol delivers only reward legs with no durable mark, so XP/item legs never double-deliver, and faction/status/intent/marks commit in one write.
- Ineligible intents (quest removed, state moved on, objectives withdrawn) stay pending and are counted as unresolved for manual recovery — fail closed, never guessed.
- Stale intents on already-COMPLETED quests are dropped durably; a failure to persist that cleanup is counted unresolved.
- Restart fixture `loginRecoveryResumesInterruptedRewardFanOutExactlyOnce` proves a crash mid-fan-out resumes after restart and delivers exactly the unmarked leg once. `loginRecoveryResumesEligibleIntentWithoutRewardMarks` covers the crash-before-first-mark window. Stale-intent cleanup and ineligible fail-closed behavior are each covered.
- Full suite after this pass: `BUILD SUCCESSFUL`, 55 suites, 484 tests, 0 failures. No live MC testing.

### Residual limits added by this pass

- A pending intent is only resumed when `isPendingQuestCompletionEligible` holds — an explicit `completeQuest` that bypassed objectives and then crashed leaves an intent whose eligibility can never be proven; it stays pending for manual recovery, matching `retryPendingQuestCompletion` semantics.
- `recoverQuestCompletions` returns a count only; per-intent diagnostics are logged per quest, consistent with the bank/trade recovery surface.
- Marked-but-possibly-undelivered legs remain prefer-loss-over-duplicate, as documented in `completeQuestUnderLock`; recovery reports but does not re-deliver them.

## P2-3 review-remediation pass — economy exactly-once gaps

Independent review found three exploitable defects in this slice; all three are remediated with regression fixtures:

- **Trade under-charge with identical inputs.** `TradeListing.validate()` previously validated each input leg independently, so a listing like `40 emerald + 40 emerald` passed two independent held-checks against the same inventory and under-deducted. `validate()` now rejects identical primary/secondary item IDs, and `executeTradeMutationCore` additionally asserts each deduction loop consumed the full requested amount — on any shortfall the catch restores every removed stack (`ItemStack.grow` on the recorded paid stacks) and rolls back the owned reservation. Regression: `identicalTwoInputListingIsRejectedBeforeAnyExchange`.
- **Unjournaled withdrawal compatibility path.** `withdrawAndDeliverFromBank(uuid, repo, tab, slot)` carried a `null` request ID down an explicitly untracked leg. The untracked path no longer exists: `withdrawAndDeliverInternal` mints a fresh `UUID` when the caller supplies none, so every whole-stack withdrawal holds a `bank.withdraw` journal record; the former unjournaled helper is renamed `withdrawAndDeliverCore` and is only reachable inside the journal. Regression: `compatWithdrawalWithoutRequestIdJournalsOperation` blocks the vault transaction mid-flight and asserts a `STARTED bank.withdraw` journal record exists during the compat call.
- **Quest-mail claim TOCTOU.** `QuestMailStore.claim()` was a check-then-write across two separately synchronized store calls, so two concurrent claimants could both succeed and duplicate reward delivery. The claim now runs through `IndexedRecordStore.computeIfPresent` — read, claimed-check, mark, and durable write as one critical section under the store monitor. Regression: `concurrentClaimsOnTheSameMailSucceedExactlyOnce` races 16 claimants and asserts exactly one success, durable across reopen.

## P2-3 pass — durable dedup for faction/transport (exactly-once)

The remaining request-id replay guarantees were in-memory only (`completedFactionMutations`, `completedTransportRequests` caches die with the process). This pass makes the value-moving typed operations exactly-once across restart:

- **`PlayerProgression.appliedActionRequests`** — a bounded (512-entry FIFO) durable ledger recording `requestId -> fingerprint\noutcome` inside the same atomic progression save as the mutation it keys. Crash between mutation and save rolls the marker back with it via the existing snapshot/restore path; a committed marker means the effect provably committed.
- **Faction mutations** (`mutateFactionProgression`): durable replay check inside the progression critical section after the in-memory cache. A recorded request id returns the stored revision/events as `duplicate=true` without re-applying — a replayed non-idempotent `ADJUST` can no longer double-apply after restart. A reused id with a different payload is `REQUEST_PAYLOAD_MISMATCH` durably, not just in memory.
- **Transport unlock** (`unlockTransportLocation` typed overload): the unlock grant and the request marker commit in one progression save; post-restart replay returns the recorded outcome (`REPLAYED`) and a rebound location is `REQUEST_PAYLOAD_MISMATCH`.
- **Transport request** (`requestTransport` typed overload): now journaled through a dedicated `transport-operations` `DurableOperationJournal` instead of an in-memory cache. Fresh requests still evaluate authorization first — denials are never journaled, so a retried request id re-evaluates under changed privilege. Executed attempts are terminal-journaled (`commit` on applied, `abort` on rejected/compensated) with the `TransportResult` encoded in the record detail; post-restart replays decode and return it verbatim without re-charging or re-teleporting. A durable `PREPARED` record — a crash between prepare and terminal transition over live inventory/teleport side effects — returns `RECOVERY_REQUIRED` fail-closed and is surfaced by the new `recoverTransportOperations` login sweep wired into `WorldLifecycleHandler.handlePlayerLogin`.
- `DurableOperationJournal` now distinguishes `OperationIdentityMismatchException` (request-id binding conflict) from storage failures so adapters can map it to `REQUEST_PAYLOAD_MISMATCH` instead of a generic journal failure.

New fixtures (`P23ExactlyOnceTest`): restart-replay of faction ADJUST applies once; durable payload-mismatch rejection; restart-replay of transport unlock; journaled terminal outcome replay for transport requests; planted `PREPARED` record fails closed + recovery sweep counts it; request-id reuse across locations rejected.
